1. How we ran the experiments

The lab suggests an in-IDE agent such as Cline. We used Claude Code, a comparable coding agent that reads and edits the files of a project itself. For each experiment:

  • We exported a fresh copy of our repository into an empty folder and started a new agent session there, so the agent had no memory of earlier work and could not see our real working copy. We removed CLAUDE.md (our notes for AI tools) from the copy, because it describes HygieneController's rules in prose and would have given the answer away.
  • The agent could read, search, create and edit files in the copy, but could not run commands. We ran the test suite ourselves afterwards, so we could see exactly what it changed and judge it against the same tests we use.
  • We compared its files with the originals (diff) and ran our full backend test suite (pytest), which includes the Lab 4 black-box and basis path tests.

The exact prompts and the agent's replies are in the appendix. The files it produced are kept in docs/lab4/agent_experiments/ in our repository.

2. Exercise 3.3.2: regenerating HygieneController

What we did

We chose HygieneController, the control class we black-box tested (section 1 of our Lab 4 test cases). We deleted the whole file, backend/app/controllers/hygiene_controller.py; with it gone, the test suite could not even start (an import error during collection). We then gave the agent one prompt (appendix A.1) telling it the file had been deleted and pointing it to:

  • our tests, especially the Lab 4 black-box tests of passes_threshold;
  • the code that calls HygieneController;
  • our design class diagrams and the requirements cited in code comments (FR-2.1 to FR-2.5).

We did not give it the original class, not even with the function bodies removed.

Result

Other files changedNone (checked with diff)
Test suite on its class127 passed, 1 skipped, 1 warning in 6.07s, the same as with our original class

The agent rebuilt the class with the same public interface as ours: the GRADE_RANK ordering A > B > NEW > C and the four methods current_grade, passes_threshold, summary and track_record, with the same signatures. It worked these out from the callers and the class diagrams, and the rules from the tests: for example, that a stall with no current grade fails any minimum, and that a snapshot older than the latest SFA export means the grade is no longer current. It added docstrings citing the requirements, and sorted the grade history by date instead of relying on the database's ordering.

Comparing it with our original, line by line, showed two differences in behaviour that none of our tests detected:

  1. summary() counts only Cooked Food stalls; ours counted every stall passed to it. Our SFA import only keeps Cooked Food stalls (all 5,614 stalls in our data are), so this makes no visible difference today; the agent's version is the more defensive one (FR-1.6).
  2. track_record() lists every grade snapshot; ours collapses consecutive identical snapshots so the history shows only changes. Every licence has one snapshot so far, so the two look the same now, but after a few months of daily SFA imports the agent's version would show dozens of identical "A" rows on a stall page. This would be a real regression, and our tests only check that the history is not empty.

It also turned our comment "Team to confirm this choice" about where NEW ranks into a settled statement citing FR-2.2.

A second run of the same prompt happened by accident after the first had finished. That session found the agent's own new file, took it for the original and refused to overwrite it, saying a rewrite after reading it would not be a valid "from scratch" result (appendix A.3). It did not change anything.

Reflection

The outcome exceeded our expectations: the agent rebuilt a working class in one attempt, from tests and diagrams alone, without seeing the original or running the tests. Its explanation was accurate and traced each decision to a test or a requirement. The experiment also showed how much it relied on our tests to define "correct": where a behaviour was only in our code and not in a test or a diagram (collapsing the grade history), it reasonably chose something else, and the suite still passed. The lesson for us is that our tests are the real specification when an AI writes code, so the gap to close is a test for the collapsed grade history. Had the agent failed, the next steps we had planned were to paste the test failures back to it, then to give it the original file with only the function bodies removed.

3. Exercise 3.3.3: code quality review and refactoring

What we did

Our further experiment was the lab's third suggestion: ask the agent for its opinion on the quality of our codebase, and have it carry out one of its refactoring suggestions. In a new fresh copy and a new session, we asked it (appendix B.1) to rank the five refactorings that would most improve the backend, with reasons and risks, then to carry out only the top one without changing behaviour or tests, and to explain how it made sure behaviour was unchanged.

Result

Agent's workAbout 3 minutes 10 seconds over 43 steps of reading and editing
Files changed4 controller files, 48 changed lines; no tests changed
Test suite before and after127 passed, 1 skipped, 1 warning in 5.93s after, the same as before
Our extra checkThe original and refactored centre list and recommendations give identical results on our real data in all 15 scenarios we tried (every minimum grade, with and without the halal restriction)

Its five suggestions (in full in appendix B.2):

  1. define each stall-filtering rule once;
  2. share the centre query and the Cooked Food filter;
  3. split up the 100-line recommend() method;
  4. move business logic out of the API router;
  5. cut the per-row database queries in the SFA import.

Each came with a specific reason and a sensible risk. For example, for number 5 it warned that a licence appearing twice in one export would behave differently, and said to add a test for that first.

The refactoring it carried out (number 1) was well chosen:

  • One rule instead of three. Our minimum-grade rule (FR-2.5) was written out in three places: passes_threshold, the cached centre list and the recommendations. The halal check and the suspension flag were each written twice. It added HygieneController.grade_passes() and suspended_past_year() and made every caller use them.
  • It caught an error in our own documentation. Our Lab 4 test document says the centre list and recommendations use passes_threshold(). They had kept their own copies of the rule since we added caching, so our 16 black-box tests only covered one of the three copies.
  • It named a remaining gap. No test checks which centres the minimum-grade filter returns.

Reflection

This met and in places exceeded our expectations. The review was specific to our code rather than generic advice, the ranking was reasonable, and the refactoring was small, safe and easy to check. Its "proof" that behaviour was unchanged was careful reasoning, not a test run, since it could not run commands; we confirmed it with the test suite and the real-data comparison. The most valuable result was finding the mismatch between our test document and our code, which a human review had missed. Adopting this refactoring would make the rule our black-box tests cover the one every list uses, and the missing centre-list test would close the gap it found. Its suggestions 3 and 5 are medium risk, and we would only attempt them with new tests in place first, as it advised.

Design decisions:

  1. Grade order A=4, B=3, NEW=2, C=1 (FR-2.2). NEW sits above C so it never looks like a failing grade, which tests BB-07 and BB-08 check. All ranks are above 0 because HawkerCentreController._cached_summaries uses default=0 to mean "no graded stall".
  2. current_grade(licensee) (FR-2.1). It takes the newest snapshot, sorted by date. It doesn't rely on the database's ordering because the Lab 4 tests build objects in memory. If that snapshot is older than last_seen_snapshot, it returns None: the latest SFA export listed the licence without a grade, such as "Not Under SAFE". Tests BB-14, BB-15 and the ETL "Not Under SAFE" test cover this.
  3. passes_threshold(stall, threshold) (FR-2.5, FR-5.4). With no minimum set, every stall passes. With a minimum, a stall passes only if its grade ranks at or above it. A stall with no current grade or no linked licensee fails. This matches the rule RecommendationController already copies inline. Invalid minimums such as "D" or "a" are rejected by the API (HTTP 422) before they reach this method, so it doesn't check for them.

  5. track_record(stall) (FR-2.3, FR-2.4). It's built from the snapshots rather than stored, as the entity diagram notes.
    • Suspended flag: it comes from licence_status, which is what the ETL test needs and what stall_summary uses. The grade row can't be used because a "Not Under SAFE" export creates no grade row.
    • Last updated: this is the date of the latest SFA export that listed the licence.
    • Grade history: all grades, newest first.
    • Demerit points: this stays null because SFA doesn't publish them.
    • No licensee: it returns an empty record instead of failing.

A.4 The class the agent wrote

"""HygieneController (FR-2.1 to FR-2.5).

Works out a stall's current SAFE grade from the dated SFA snapshots, its track record,
and whether it meets a user's Hygiene Threshold (also used for FR-5.4)."""

from collections.abc import Iterable

from ..models import Licensee, SAFEGrade, SafeGradeValue, Stall, StallType
from ..schemas import GradeSummary, SafeGradeOut, TrackRecordOut

# A > B > NEW > C. NEW (licensed under a year) ranks above C because SFA says it
# must not be presented as a failing grade (FR-2.2). All ranks are > 0, so callers
# can use 0 for "no current grade".
GRADE_RANK = {SafeGradeValue.A: 4, SafeGradeValue.B: 3, SafeGradeValue.NEW: 2, SafeGradeValue.C: 1}


def _history(licensee: Licensee) -> list[SAFEGrade]:
    # Newest first. The relationship is already ordered that way when loaded from the
    # database, but objects built in memory may not be
    return sorted(licensee.grades, key=lambda g: g.snapshot_date, reverse=True)


class HygieneController:
    @staticmethod
    def current_grade(licensee: Licensee | None) -> SAFEGrade | None:
        """The newest snapshot (FR-2.1), but only if it came from the latest SFA export that
        listed the licence. An older one means SFA no longer gives it a grade there
        (e.g. "Not Under SAFE"), so there is no current grade."""
        if licensee is None or not licensee.grades:
            return None
        newest = _history(licensee)[0]
        if licensee.last_seen_snapshot and newest.snapshot_date < licensee.last_seen_snapshot:
            return None
        return newest

    @staticmethod
    def passes_threshold(stall: Stall, threshold: SafeGradeValue | None) -> bool:
        """True if the stall's current grade ranks at or above the minimum (FR-2.5, FR-5.4).
        With no minimum every stall passes; with one, a stall with no current grade (or no
        licensee) fails, so ungraded stalls are never shown to someone who asked for a minimum."""
        if threshold is None:
            return True
        g = HygieneController.current_grade(stall.licensee)
        return g is not None and GRADE_RANK[g.grade_value] >= GRADE_RANK[threshold]

    @staticmethod
    def summary(stalls: Iterable[Stall]) -> GradeSummary:
        """How many of a centre's Cooked Food stalls (FR-1.6) hold each current grade."""
        counts = {"A": 0, "B": 0, "C": 0, "NEW": 0, "ungraded": 0}
        for s in stalls:
            if s.stall_type != StallType.COOKED_FOOD:
                continue
            g = HygieneController.current_grade(s.licensee)
            counts[g.grade_value.value if g else "ungraded"] += 1
        return GradeSummary(**counts)

    @staticmethod
    def track_record(stall: Stall) -> TrackRecordOut:
        """Built from the snapshots, not stored (FR-2.3, FR-2.4). SFA only publishes a
        "suspended in the past year" flag, not demerit points, so total_demerit_points stays null."""
        lic = stall.licensee
        if lic is None:
            return TrackRecordOut(suspended_past_year=False, grade_history=[], last_updated=None)
        return TrackRecordOut(
            suspended_past_year=lic.licence_status == "suspended",
            grade_history=[SafeGradeOut.model_validate(g) for g in _history(lic)],
            last_updated=lic.last_seen_snapshot,
        )

I've ranked five refactorings below and done the top one. I couldn't run anything here, so the test suite hasn't been run yet.

1. The five refactorings, ranked

1. Define each stall-filtering rule once (done, details below).

  • Why: the minimum-grade rule (FR-2.5) was written out three times. HygieneController.passes_threshold had it, the centre list kept its own grade-number comparison, and the recommendations kept a third copy with a comment saying "Same rule as…". The halal check and the "suspended" flag were each written twice.   • Risk: low. Each change swaps code for an equivalent call. The only change in shape is in-memory cached data that nothing outside the controller reads.

2. Share the centre query and the Cooked Food filter.

  • Why: _centre_query() and _cooked() in hawker_centre_controller.py are copied by hand into recommendation_controller.py:47-62. The stall loading options are repeated in search and stall_detail.   • Risk: low. If the shared query loads less up front than the copy did, you'd get many extra database queries (much slower), but the results wouldn't change.

3. Split up RecommendationController.recommend (about 100 lines).

  • Why: loading the user's data, the filters, six counters, the scoring weights and the per-centre limit are all in one loop. The scoring is the logic you're most likely to tune, and right now it can't be tested on its own. Pull out a small user-context object, a _score(...) -> (score, reasons) function and a _cap_per_centre function.
  • Risk: medium. The order of the reasons, the floating-point sums and the tie-breaks all have to stay exactly the same. Write unit tests that pin the current output before moving anything.

4. Move business logic out of routers/public.py.

  • Why: the router works out freshness and staleness, picks the default dish profile, decides the halal default and calls OneMap directly. Your class diagrams describe routers as a thin layer over the controllers. The "SQLite drops the timezone" fix also exists twice (user_controllers._utc and an inline copy in freshness).
  • Risk: low to medium. Watch for import cycles. Tests that patch httpx will have to patch it in the new module, which means editing tests, so do that step on its own.

5. Cut the per-row database queries in the ETL scripts.

  • Why: sfa_import.load runs up to three queries for every row (licensee, stall, grade). That's tens of thousands of round trips per full export against Supabase. Load them all up front into dictionaries. Smaller fixes alongside it: seed_reference.load reads the rules CSV twice, and nea_sync.parse_row repeats the closure-reason logic.
  • Risk: medium. Sessions are created with autoflush=False, so today a licence that appears twice in one export probably fails when the data is saved. With dictionaries, the second row would quietly update the first instead, which changes behaviour. Add a test for duplicate rows first.

How I checked the behaviour is the same

I compared old and new code case by case:
