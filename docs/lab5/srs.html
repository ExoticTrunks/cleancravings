1. Introduction

1.1 Purpose

This document specifies what CleanCravings does, for the team, the course markers and anyone extending the system. Version 2.0 brings the Lab 1 to 3 requirements and use case model in line with the working prototype demonstrated in Lab 5: each requirement now states whether it is implemented, and wording has been changed where the original assumed data that no open dataset provides.

1.2 Scope

CleanCravings is a responsive web app that helps diners in Singapore choose where to eat at hawker centres. It brings together official data: SFA's SAFE food hygiene grades, NEA's hawker centre list and closure dates, and HPB's Healthier Dining Programme. Anyone can find centres and stalls, filter by hygiene, distance and region, get clean, nearby stall picks and see common hawker dishes rated against HPB-based nutrient thresholds. Signing in with Google adds a health profile, bookmarks, closure alerts and a private visit log. The app gives general guidance; it is not a medical or food safety guarantee.

1.3 Definitions

TermMeaning
SAFE gradeSFA's Safety Assurance for Food Establishments grade: A, B, C, or NEW for licensees with under a year of record. NEW is not a failing grade.
Track recordA stall's grade history (from the team's dated snapshots of SFA data) and whether its licence was suspended in the past year.
Closure PeriodA dated closure of a whole hawker centre from NEA: spring cleaning, repairs and redecoration, or other works.
HDPHPB's Healthier Dining Programme; participating stalls are "Healthier Dining" stalls.
Dish typeA common hawker dish (41 of them) with typical nutrient values, rated by the rule engine.
Classification ruleOne row of the team's rule table: condition, nutrient, operator, threshold, verdict and citation.
VerdictA dish rating shown as Good choice, Have in moderation, Have occasionally, or Not enough data.
Guest / Signed-in DinerA user who hasn't signed in / a user signed in with Google.

2. Overall description

2.1 Product perspective

CleanCravings is a new, self-contained system with three parts:

  • Web app (React and TypeScript): every page, for phones and desktops.
  • Backend API (Python FastAPI): the only thing the web app talks to (NFR-5). Thin routers pass requests to control classes (hygiene, closures, recommendations, healthier eating, profile, bookmarks, visits, alerts), which read entity classes stored in PostgreSQL on Supabase.
  • Data sync: one module per source, run daily outside the request path (UC-12.0). A failed source keeps its last good data.

Sign-in is handled by Supabase Auth with Google; the backend only verifies the session token. Maps and place search use OneMap.

2.2 Users

User classNeeds
GuestFind clean, open centres and stalls nearby; check a stall's grade; see which dishes suit general guidance. No account needed.
Signed-in DinerEverything a guest can do, plus picks and dish ratings tailored to their health conditions and preferences, bookmarks, closure alerts and a private visit log.

2.3 Operating environment

Current Chrome, Edge, Safari and Firefox on Android, iOS and desktop. The backend runs on Python 3 with PostgreSQL (SQLite for local development and tests).

2.4 Design and implementation constraints

  • Only official open data may be shown as fact. SFA has no API, so its data comes from manual exports; history exists only from the first saved snapshot.
  • No open dataset gives a stall's dishes, cuisine, prices, contact number, operating hours or demerit points. Requirements that need them are reworded, deferred or planned (see section 3).
  • Health guidance must stay general and soft in wording (NFR-6); the app is not a medical device.
  • Personal data is handled per Singapore's PDPA (NFR-7, NFR-8).

2.5 Assumptions and dependencies

  • data.gov.sg, SFA's portal, OneMap, Google and Supabase remain available and keep their formats.
  • SFA licence numbers stay stable across exports, so grades can be linked over time.
  • Typical hawker recipes roughly match the published nutrient profiles used for dish ratings.

UC-0.1 Log In with Google and Log Out

Use Case IDUC-0.1
Use Case NameLog In with Google and Log Out
StatusImplemented
Created ByJovan Chua, 2026-09-04
Last UpdatedRafael, 2026-11-13 (v2.0)
ActorsPrimary: Guest. Secondary: Google Sign-In (via Supabase Auth).
DescriptionAllows a user to sign in with their Google account so they can save a health profile, bookmarks and visits, and receive closure alerts, and to sign out again. CleanCravings never sees or stores a password.
Preconditions
  1. The user has a Google account.
  2. The device has a network connection.
Postconditions
  1. The user is signed in, and the browser holds a session that is sent to the backend as a Bearer token.
  2. On first sign-in, the system creates the user's account record.
PriorityHigh
Frequency of UseHigh
Flow of Events
  1. User selects "Sign in" in the header, or an action that needs an account (for example Save or Log a visit).
  2. System displays the Sign-in screen.
  3. User selects "Continue with Google".
  4. System redirects the user to Google through Supabase Auth.
  5. User chooses a Google account and approves access.
  6. Supabase Auth returns the user to CleanCravings with a session, which the browser stores.
  7. Backend verifies the session token and creates the user's account record on first sign-in.
  8. If the user has no health profile yet, System opens profile setup (UC-1.0); otherwise it opens Home.
Alternative Flows

0.1.AC.1 Returning session: At Step 1, if a valid session is stored, the system signs the user in automatically.

0.1.AC.2 Continue as guest: At Step 2, the user selects "Continue as guest" and keeps browsing without an account (FR-0.1).

0.1.AC.3 Sign out: From Profile, the user selects "Sign out". The system ends the session and removes it from the device.

Exceptions

0.1.EX.1 Sign-in cancelled: At Step 5, if the user cancels, no session is created and they stay signed out.

0.1.EX.2 Session rejected: If the backend can't verify the token, the system treats the user as signed out.

0.1.EX.3 Sign-in service unavailable: At Step 4, if Google or Supabase can't be reached, sign-in fails and the user can keep browsing as a guest.

Includes / ExtendsNone
Special RequirementsNo passwords are handled or stored (NFR-8). Signing out removes the stored session, so a shared device doesn't stay signed in. Traces to FR-0.1, FR-0.2, FR-0.3, NFR-8.
AssumptionsThe Google provider is enabled in the team's Supabase project.
Notes and Changes from v1v1 described email and password sign-in with "Remember me" and "Forgot password". These were dropped when the team chose Google sign-in.

2.0.EX.2 No centres match: At Step 5 or 7, the system shows "No centres match. Try removing a filter."

2.0.EX.3 No stalls match: At Step 9, the system shows "No matches found." with how many stalls the filters hid.

UC-12.0 Refresh Official Data

Use Case IDUC-12.0
Use Case NameRefresh Official Data
StatusImplemented
Created ByRafael, 2026-11-13 (new in v2.0)
Last UpdatedRafael, 2026-11-13 (v2.0)
ActorsPrimary: Scheduler (GitHub Actions, daily at 02:00 Singapore time). Secondary: NEA and HPB datasets on data.gov.sg, SFA Track Records export.
DescriptionLoads the latest official data into the database outside the request path, one source at a time, and creates closure alerts. A failed source keeps its last good data.
Preconditions
  1. The database is reachable.
  2. For SFA: a new export from SFA's Track Records portal has been placed in etl/inbox (SFA has no API).
Postconditions
  1. Each source's run is logged with its status, time and row count, which the app shows as "last updated".
  2. New closure alerts have been created (UC-8.0).
PriorityHigh
Frequency of UseDaily (and by hand when a new SFA export arrives)
Flow of Events
  1. Scheduler starts the daily run.
  2. System loads the team's dish profiles and classification rules from CSV.
  3. System loads hawker centres and closure dates from NEA on data.gov.sg.
  4. If a new SFA export is in the inbox, System imports SAFE grades for stalls at hawker centres as a new dated snapshot.
  5. System loads HPB's Healthier Dining partners and links them to stalls by name (exact, then a guarded fuzzy match, then manual overrides, otherwise centre-level), and takes halal status from the listing.
  6. System creates closure alerts for saved centres (UC-8.0).
  7. System records each source's result; the app's caches refresh on the next request.
Alternative Flows

12.0.AC.1 No new SFA export: At Step 4, SFA is skipped and the previous snapshot stays current.

12.0.AC.2 Run one source by hand: A team member runs a single source module on its own.

Exceptions

12.0.EX.1 Source fails: The failed source rolls back and keeps its last good data; the other sources still run.

12.0.EX.2 Data goes stale: If a source hasn't succeeded for 48 hours, the app shows an "Offline mode" banner (NFR-9).

Includes / ExtendsUC-8.0 Closure Alerts (Step 6).
Special RequirementsEach source is an independent module (NFR-10); the app only reads what is already in the database (NFR-5). Traces to NFR-2, NFR-4, NFR-9, NFR-10, FR-3.4.
AssumptionsNEA, SFA and HPB keep their dataset formats and licence numbers stable.
Notes and Changes from v1New in v2.0, because the data sync is a major part of the system and wasn't in the v1 model.
